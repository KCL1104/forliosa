> 狀態：**原型，產品負責人還沒同意**。2026-11-20 開 PR 給負責人審查；合併以前不部署。
> 這份文件是負責人的朋友和 Claude 在 2026-11-18～19 討論後整理的，還不是產品決定。

## 為什麼做

使用者的出發點：「不知道自己到底有沒有賺錢，也不知道自己什麼時候做得比較好。」

總資產變多，分不出是市場賺的，還是自己一直加碼放進去的。券商 app 只顯示現在還抱著的股票的損益。這個功能把兩件事拆開，而且匯入一張庫存截圖的當下就看得到東西。

## 估計買入日的算法

輸入：一檔持股的成本價（庫存截圖上的均價）與股數。

1. 價格用**當時真正的成交價**（Yahoo 回補的日線已照分割調整，用 `services/reference_close.py` 同一套換算乘回去）。
2. 從今天往回找，第一個「當天最低價 ≤ 成本價 ≤ 當天最高價」的日子，就是估計的買入日。用最高、最低價判斷，不用收盤價。
3. 跳空也算經過：前一天最高 600、當天最低 620、成本 612，取跳過去的那一天。
4. 回補的五年裡都找不到，就不估：買入日是匯入那天，和現在一樣。
5. 估計的那一筆買進：價格仍是券商的成本價、手續費 0，只有日期是估計的，另外記一個標記（估計／自己選的／一般）。

使用者自己選：打開那一檔的走勢圖，一條橫線標出成本價，橫線與走勢交會的日子是候選，自動選的那個先標起來；點任何一天就改成那天。選了離成本價很遠的日子時照實寫差距（「這天收盤 580，和你的成本 612 差 5%」）。自己選過的標「自己選的日期」，不再標「估計」。

限制（畫面要誠實）：
- 估計的區間不算年化報酬，不進「每月報酬率」。
- 分批買、定期定額的人，成本價不對應任何一天；第一版只支援一個日期。
- 領過配股的持股，券商的成本被攤低，可能對不到或對錯日子。
- 美股的歷史只從 2024-07 開始，更早的找不到。
- （檢查點 2 加的，審查後擴大到配股）券商的股數與均價是匯入那天的，已經算進之前每一次股票分割、減資、配股：**匯入的買進最早只能是匯入那天（含）以前最近一次分割、減資或配股（配股 > 0）的那一天**（那天本身可以：那天的股價已經是改過股數以後的）。估計只往回找到那天（那天的「跳空」也不算經過）；送出匯入、改日期都不收更早的日子；選日期的畫面不列更早的日子。買在那天以前的話，帳本會拿現在的股數乘當時的價格，配股也會被股利自動入帳再記一次（審查重現過：配股 5% 的 1,050 股變成 1,102 股）。分割、減資、配股的日子和帳本記它們用的是同一份資料（目錄裡已知的分割與減資、存檔偵測到的美股分割、存檔的除權預告）。見附錄 B〈後端實作（檢查點 2）〉。

## 要產品負責人決定的事

1. Yahoo 回補的日線拿來估計買入日、畫估計的歷史走勢（比現在允許的用途多一項）。**檢查點 2 的後端已經這樣做了（待負責人同意）**：匯入庫存的估計（`services/buy_date.py`）與選買入日的日線（`GET /instruments/{symbol}/history?prices=as_traded`）都讀 Yahoo 回補、換算回當時的成交價；回補關掉或刪掉時只用官方存檔的日子，估不到的句子照實寫從哪一天開始找。不同意的話把這兩個地方改成只讀官方存檔（估計幾乎都會找不到，退回「匯入那天」）。
2. 基金淨值從只存 ETF 擴大到存所有境內基金，用來算「贏過幾 % 的基金」。**檢查點 2 沒有做**：配息的基金要加回配息，現有的來源檔（data.gov.tw 11109）沒有配息資料，不能加新的來源，所以 `fund_rank` 一律 null（附錄 B〈基金排名〉）。
3. 散戶排名的匿名統計：要改隱私權政策，也要問律師。
4. 匯入庫存原本「整批一個日期，預設今天」的做法，改成每一檔預設用估計的買入日。
5. **總資產走勢塗色（v2）**：DESIGN.md〈總資產走勢〉現在寫「不填色、沒有動畫」與「縱軸只看總資產，投入本金有任何一天不在範圍裡就整條不畫」。v2 在本金線和總資產之間塗淡色（賺／虧），縱軸在總資產起伏夠大時也把本金放進來，本金在圖外時照畫（切在圖的邊緣）、圖裡寫一行在哪一邊。這三點都和 DESIGN.md 不一樣，要負責人同意才能進主線；DESIGN.md 沒有改。走勢旁邊的「本金」開關關掉時只有總資產一條線，是最接近 DESIGN.md 現在的樣子（另一個選項：預設關、想看的人再打開）。2026-11-20 起 main 的走勢是墨色線＋淡出的墨色面積（DESIGN.md〈走勢圖規格〉）：本金開著時塗色**取代**淡墨面積（不疊兩層），關掉時照 main 畫淡墨面積，看起來就是 main 的走勢（多了股利記號與「估計」）。高度、區間按鈕的位置也照 main（桌面 120、手機 96；桌面的區間按鈕在讀數那一列的右邊）。細節見附錄 A〈A〉。

## 已知問題

- **計算成本**（檢查點 2 量過，數字與做法見附錄 B〈計算成本〉）：估計買入日本身很便宜（每檔最多掃約 1,200 列、只在匯入時算一次），但它讓帳本的歷史從幾天變成最多五年。本機 SQLite 量到：20 檔、五年歷史的帳本，績效每個區間約 0.28 秒（只有匯入那天的同一個帳本 0.02 秒）；50 人、每人五年歷史的群組排行約 1.2 秒（每人只有幾天的 0.2 秒）。資產組成本身只多幾毫秒。建議先快取 Yahoo 回補換算成當時成交價的日線（佔績效時間約六成），見附錄 B。
- **基金淨值的歷史**：來源檔只有最新一天，歷史要從開始存的那天累積；淨值不含配息，有配息的基金要另外調整。檢查點 2 沒有做（`fund_rank` 一律 null），原因見附錄 B〈基金排名〉。
- **對帳單補歷史**：先匯入庫存、之後再匯入對帳單，會不會和庫存匯入的那一筆重複計算，還沒有確認。
- **配股的除權日到發放日之間匯入**：規則假設匯入那天券商的股數已經含那次配股。台灣的配股要在除權日後幾個星期才撥進帳戶，這段期間截圖上的股數可能還是舊的；這時買進日期最早只能是除權日，帳本就不會記那次配股（少算配股的股數）。沒有處理，要的話可以讓使用者自己記那筆配股。
- **存檔開始以前的配股不知道**：除權預告只從存檔開始的那天才有，之前的配股不是限制（股利自動入帳也不知道它們，所以不會重複計算），但 Yahoo 的日線可能把那次配股當成分割換算過，估計可能對錯日子（和〈估計買入日的算法〉「領過配股的持股」同一個問題）。
- **自己選了離成本很遠的日子**：買進價仍是券商的成本，所以那一天的總資產會跳一下（示範帳號的元大高股息選 2024/3/11，那天收盤比成本低很多，時間加權報酬那天 −19%）。選日期的畫面已經照實寫差幾 %（附錄 A〈E〉），報酬會被影響這一點沒有寫。

## 以後的選項：帳戶現金（D 方案）

> 狀態：**沒有做**。2026-11-19 使用者提出、開始做原型以後又撤回：系統會變得太大。原型的程式已經全部拿掉（這個分支裡沒有），只留這一段當以後的選項。現在的做法是上面決定 5 的「本金已收回」。

照券商 app「淨入金」的想法，app 開始記每個券商帳戶裡的現金：

- **帳戶現金**：每個券商帳戶、每個幣別各一份。賣出收到的錢（扣掉手續費與稅）、減資退款留在帳戶裡，當成帳戶現金；不會小於 0。
- **買進先用帳戶現金付**：帳戶現金不夠付的那一部分才是「放進去的新錢」（不用另外記「轉入」）。
- **本金**＝放進去的新錢－轉出。**只有新錢與轉出會改變本金**；賣出、買進（用帳戶現金付的部分）都不動本金。
- **總資產**＝持股市值＋帳戶現金。
- **賺的不變**：總資產－本金＝（持股＋帳戶現金）－（新錢－轉出）＝持股－（買進－賣出收到的錢），和現在的算法一樣，不管買賣、轉出的順序怎麼排都一樣（美元帳戶的現金放著時匯率變動會算進來，這一點不一樣）。轉出時總資產和本金減一樣多，賺的也不變。所以走勢圖的**塗色面積一樣**，只有塗色那一塊的位置（高低）跟著帳戶現金移動；賣出那一天總資產與本金都不會往下掉（股票換成現金），也不會再有「本金已收回」那種塗色比賺的少的情況。
- **本金只有在轉出的錢比放進去的新錢還多時才會是負的**（例如本金 100 萬賺到 300 萬，再轉出 250 萬）。
- **成本**：
  - 記一筆多一個「轉出」類型（帳戶、日期、金額；不能超過那個帳戶那一天的帳戶現金），交易表單、交易清單、API、匯入都要跟著改。
  - 後端 `domain/performance.py` 的績效重播要照帳戶、照幣別重算每一天的帳戶現金（買進先扣現金、不夠的才算新錢），績效序列多帳戶現金與新的本金兩個欄位。
  - 主數字的「總資產」改成含帳戶現金：PRODUCT.md 與 DESIGN.md 的總資產定義都要改，要產品負責人決定。報酬（時間加權）、XIRR、和 0050 比、每月報酬率、群組排行、配置照舊只看持股。
- **風險**：
  - 使用者把錢轉回銀行（或轉到另一家券商買股票）、忘了記「轉出」，總資產會一直多算那筆錢（還以為錢在帳戶裡）；轉到另一家買的那一筆還會再算一次新錢。
  - 券商對帳單匯入看不到銀行那一邊的轉帳，「轉出」只能使用者自己記。

- **買進、賣出那一天，兩條線一起垂直跳**（第二次審查 1）：總資產線在兩個收盤之間只畫價格的漲跌——斜到那一天「買賣以前」的值（`v[i] − (p[i] − p[i−1])`），在那一天和本金一起垂直跳同樣的金額（`totalPreFlow`、`flowPathOf`）。所以**每一個收盤日的左邊，塗的顏色就是那天收盤的賺或虧**（`v[i] − p[i]`），垂直跳的時候賺的多少不變。以前（第一版 v2）整段拿前一天的本金比，買賣金額比當時累積的賺賠大的那一天會有一塊顏色相反的三角形：`?mock=cashout` 10/20 整批賣出，收盤都是賺的，1 月卻塗了一塊 28×46px 的「虧」；虧 2 萬時買進 30 萬會有一大塊「賺」；最後一天買進 50 萬、跌 1.5 萬，右邊的盡頭塗成賺、圖例卻寫虧的。這幾種現在都有測試（每一個收盤的左邊是那天收盤的顏色）。本金關掉時總資產線照以前的折線。

### B：股利的記號

- 圖的下緣、橫軸的日期上面一個 2px 的短直線（淡墨），每個領到股利的日子一個；圖例多一項「❙ 股利」（CSS 畫的短線，不是 Unicode 符號）。v2 不把股利疊進圖裡（決定 4）。
- 滑過、方向鍵到那一天：讀數寫「領股利 NT$5,000」（桌面在第一行；手機在第二行，和報酬同一行）；報讀器念「…，領股利 NT$5,000」。記號只有 2px，滑鼠在 5px 以內就對到那一天。
- **股利的日期對到收盤日**：週末、假日領的算在下一個收盤日（`snapDividends`）——記號、滑過的讀數、句子都用這一天。審查前週末領的沒有記號、滑不到，卻算進句子。
- **從基準收盤起算的區間，基準收盤那天的股利不算進區間**：句子不算，記號、圖例、滑過的讀數也都不放（審查前有記號卻不在句子裡）。「全部」從 0 起算，那天的照算。
- 股利不算在總資產與賺的裡（決定 3、4），所以記號放在橫軸、不放在任何一條線上。沒有用個股走勢圖的「D」字母記號：五年的區間有幾十個股利日，字母會疊成一團。

## 附錄 B：API 草稿（原型）

所有新欄位都是選填；舊版後端沒有時前端照舊（mock 的 `?composition=off` 就是拿掉這些欄位）。型別在 `apps/web/src/api/types.ts`。

### `GET /portfolio/performance` 多兩個欄位

```jsonc
{
  // …原本的欄位…
  "composition": {
    // 這段期間每一天領到的現金股利（新台幣，扣掉預扣稅與二代健保），由舊到新；沒領的日子不列。
    // 區間的第一天起（1D／5D 是基準收盤的下一天起，和 dividends_by_month 一樣）。
    // 日期是領到的那一天；那天沒有收盤（週末、假日）時前端算在下一個收盤日（見下面）
    "dividends": [{ "t": "2026-09-16", "amount": 7500 }],
    // 照估計的買入日畫的那幾段（頭尾都含），由舊到新：每一次匯入（imported_on）一段——那一次匯入最早一筆還是
    // 「估計」的買進那天，到那次匯入那天的前一個交易日；重疊或連在一起（中間沒有交易日）的併成一段。
    // 沒有估計的買進、或都自己選過日期時是 []。不裁到這個區間（前端自己算重疊）。
    // （審查後改的：原本只有一段，分好幾次匯入時會把中間的真實紀錄也算成估計）
    "estimated": [{ "from": "2024-10-28", "until": "2025-11-28" }, { "from": "2026-09-17", "until": "2026-11-18" }],
    // 每個月的拆解，由新到舊；只列真實紀錄的月份（見下面）
    "months": [
      {
        "month": "2026-11", "from": "2026-11-02", "to": "2026-11-12", "whole": false,
        "flows": 0, "pnl": 128348, "twr": 0.0323, "benchmark_twr": 0.0585
      }
    ],
    "months_estimated": 1,
    // 暫定（產品負責人還沒決定）：有一筆匯入時找不到買入日、用匯入那天記的買進的月份，不列，在這裡數
    "months_import_day": 1
  },
  // 贏過幾成的台股基金；資料不夠（基金淨值的歷史還沒涵蓋這段期間、或比的基金太少）時 null
  "fund_rank": {
    "start": "2026-01-01", "end": "2026-11-11", "beat": 0.73, "funds": 812, "universe": "境內台股基金",
    "source": "金融監督管理委員會證券期貨局〈境內基金每日淨值〉（2026），依政府資料開放授權條款第 1 版",
    "notes": ["基金淨值不含配息，配息的基金照公告的配息加回"],
    // 示範資料（mock 編的數字）才有：畫面標「示範資料」、不登記來源
    "is_demo": true
  }

```

- **賺的／虧的**（程式裡叫累積損益）＝`market_value − net_invested`，不另外給；畫面上的「本金」就是 `net_invested`。`net_invested` 的定義不改（買進成本 − 賣出淨收入 − 減資退款；股利不扣）。賣股票收到的比買的多時 `net_invested` 是負的，照實給（前端照實帶負號）。v2 的塗色、縱軸規則都是前端從序列算的，API 不用多給東西。
- **區間從哪裡算起**（前端的拆解句子與那一格；後端不用另外給，但「全部」與區間比資料長的回應要和這個規則對得起來）：和 `trendWindow` 的報酬分母同一個規則——「全部」與區間比資料長（`rangeExceedsData`）時從 0 起算、寫現在的組成（`lib/asset-composition.ts` 的 `fromZero`），其他區間從基準收盤算起。
- **股利對到收盤日**：前端把 `dividends` 的日期對到當天或下一個收盤日（`snapDividends`），記號、滑過的讀數（v1 還有拆解的句子）都用這一天；從基準收盤起算的區間，基準收盤那天（對過之後）的股利不算進區間。後端可以直接給對好的日期，結果一樣。
- **每個月**（`months`）：照這個區間的收盤算，一個月（或一個月裡真實紀錄的那一段）一列。基準是那一段第一個收盤的前一個收盤（區間的第一段用區間的基準收盤；從第一筆開始時當成 0）。
  - `flows`＝本金的變化（畫面上的「本金增減」；買進正、賣出負）；`pnl`＝賺的的變化（不含股利）；`twr`＝`twr_index` 相除；`benchmark_twr`＝`benchmark_index` 相除（基準那段沒資料是 null）。
  - 估計的任何一段裡的日子不算：整個月都在估計裡的略過、算進 `months_estimated`；只有一部分在裡面的，只算真實紀錄的那幾天（`whole: false`）；一段估計整段落在月中時，那個月前後兩部分各一列。兩次匯入之間沒有碰到估計的月份照樣列。
  - `whole`：前一個收盤在上個月、而且月底以後還有收盤。
  - **從第一筆開始（沒有基準收盤）的第一個月：`benchmark_twr` 給 null**——自己的報酬含第一天（分母是 1），基準在第一天以前沒有收盤可以當分母，兩邊的天數不一樣，不比。
  - **暫定**：有 `date_basis: "import_day"` 的買進的月份——那筆的日期對到當天或下一個收盤日，在哪個月就整個月不列、算進 `months_import_day`；在區間的基準收盤以前的不算。產品負責人選 (B) 時改成照樣列、另外標出來。
  - 前端的純函式 `lib/asset-composition.ts` 的 `monthlyBreakdown` 是同一個算法（mock 用它），可以拿來對答案。
- **XIRR**：區間碰到估計的任何一段時 `xirr: null`（估計的區間不算年化報酬）。
- **估計的那幾段在區間裡是哪幾天**：前端看這個區間畫出來的每一點，含基準收盤（`composition-text.ts` 的 `trendEstimatedText`；首頁走勢與績效分段同一個規則）；畫出來連在一起的幾天算一段。
- **基金**：今年第一個交易日到最新淨值那天，帳本的時間加權報酬和每一檔基金同期的淨值報酬比（配息照公告加回），`beat`＝報酬比帳本低的基金數 ÷ `funds`。今年有估計的那一段時，從估計那一段結束後的第一天起比（`start` 照實寫）。資料來源要擴大到所有境內基金（「要產品負責人決定的事」第 2 項）。

### `GET /instruments/{symbol}/history?range=5Y&prices=as_traded`

選買入日用的日線：存檔開始以前的 Yahoo 回補**換算回當時的成交價**（`services/reference_close.py` 同一套分割、減資換算乘回去），存檔以後是官方收盤；美股從 2024/7/1 起（Databento，本來就沒有還原）。回應和現在的 `History` 一樣，`notes` 多一句「2026/05/29 以前的股價來自 Yahoo Finance，不是官方資料」，`sources` 多列 Yahoo。舊版後端不認得 `prices` 參數，回原本照分割換算過的價格——但舊版後端也不會給交易 `date_basis`，前端不會打開選日期的畫面。

審查後多一個參數、一個欄位：

```jsonc
// GET /instruments/2881/history?range=5Y&prices=as_traded&until=2026-11-19   （until：那一筆的匯入那天，不給是今天）
{
  // …原本的 History…
  // 匯入的買進最早可以是哪一天：until（含）以前最近一次股票分割、減資或配股（配股 > 0）的那一天，那天本身可以。
  // reason：split 股票分割｜reduction 減資｜stock_dividend 配股。沒有是 null；沒有 prices=as_traded 時也是 null
  "pick_from": { "date": "2025-08-14", "reason": "stock_dividend" }
}
```

- K 線照樣從區間的第一天給（不裁），前端拿掉 `pick_from` 以前的。`pick_from` 那天以前的分割、減資不再寫在 `notes`（選日期的畫面自己寫那一行），資料比 `pick_from` 更早開始時「資料從 … 開始」也不寫。
- 「以前的股價來自 Yahoo Finance」與 `sources` 的 Yahoo 只看回應裡的 K 線：5 日讀 30 天再取最後 5 根，以前用讀到的 30 天判斷，5 根都是官方收盤時也寫 Yahoo（審查第 3 項）。

### 交易（`Transaction`）多三個欄位

```jsonc
{
  "date_basis": "estimated",      // estimated 估計的｜picked 自己選的｜import_day 找不到、用匯入那天；一般記的是 null
  "estimated_date": "2025-07-02", // 自動估的那天（自己選過也留著）；import_day 是 null
  "imported_on": "2025-11-29"     // 匯入那天（估計從這天往回找；自己選也不能晚於這天）。可以是週末或收盤前
}
```

- `PATCH /transactions/{id}` 接受 `date_basis: "picked"`；`date_basis` 不是 null 的那一筆改了 `trade_date`（不管從選日期的畫面還是完整表單）就變成 `picked`。日期晚於 `imported_on` 時 422；早於分割、減資、配股的限制（`pick_from` 同一個規則，看 `imported_on`）時 422 `before_share_change`。
- 那一筆改成別的種類（不是買進了）或別的股票：變成一般的紀錄，三個欄位都清成 null（估計與匯入那天是原本那一檔的買進的）。只改價格、股數不動這三個欄位。
- 帳本上的日期那天沒有收盤（週末、假日、收盤前匯入）是正常的：選日期的畫面打開時對到前一個收盤日，不會自己改。
- 其他欄位（價格、股數、手續費）不因為改日期而變；前端送 `trade_date` 時會把原本的 `fee`、`tax` 一起送（後端改了輸入時沒送的費用當 0）。

### 匯入庫存

- `POST /imports/positions`：每一列多 `estimated_date`（字串，或 null＝五年內股價都沒有經過成本價）。估不到時多一個旗標 `{ "code": "no_crossing", "severity": "warning", "message": "五年內的股價都沒有經過均價 120，沒辦法估買入日。" }`（美股：「美股的股價只有 2024/7/1 以後的，都沒有經過均價 US$…，沒辦法估買入日。」）。融券、找不到股票、沒讀到成本的列沒有這個欄位。
- 估計的算法照本文〈估計買入日的算法〉：從今天（台北）往回，當天最低 ≤ 成本 ≤ 當天最高，或成本落在和前一天之間的跳空缺口，取往回第一個碰到的（也就是最近一次）；價格是當時的成交價。前端的 `lib/buy-date.ts` 是同一個規則（選日期的畫面在瀏覽器裡算候選）。
- `POST /imports/positions/commit`：每一列多 `date_basis`（`estimated`｜`picked`｜`import_day`）與 `estimated_date`；伺服器照存，`imported_on` 是今天（台北）。估不到的列跟著整批的日期：整批日期沒改過才是 `import_day`，使用者把整批改成別天時前端送 `picked`。估計的那幾筆和其他匯入的一樣手續費 0。舊的前端不送時和現在一樣。
- 有 `date_basis` 的列，伺服器另外檢查（審查後加的；錯誤和其他列的錯誤一樣：dry_run 寫在那一列的 `flags`，真的寫入時 422 `batch_rejected`、`rows` 列出來，整批都不寫）：
  - `before_share_change`：日期早於那一檔匯入那天（含）以前最近一次分割、減資、配股——「2025/8/14 配股，買進日期不能早於這一天。」
  - `bad_estimated_date`：`estimated_date` 不是估得到的日子——五年前（美股 2024/7/1）以前、分割減資配股以前，或晚於匯入那天——「估計的買入日 2025/8/1 不在估得到的期間（2025/8/14 – 2026/11/19）。」（以前晚於匯入那天的估計只是不存，現在整列不收）
  - 沒有 `date_basis` 的列（一般的紀錄、舊的前端）照舊，不檢查這兩項。
